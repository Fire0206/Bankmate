# FinOrch 六场景后端实施手册

## 目的

这份手册给负责后端的同学使用：在不重写现有卡片切片的前提下，按统一契约逐步实现六个银行场景。

它不是替代 `docs/agent-contract.md`、`docs/api-contract.md`、`docs/data-contract.md` 和 `docs/security.md`，而是把六场景拆成可实现的垂直切片、工具、状态、确认、审计和测试。

## 当前基础

Phase 1A 已提供 SQLite、SQLAlchemy、Alembic、合成 Demo actor、卡片实体、任务/步骤/工具执行/确认/审计和 seed/reset。

Phase 1B 已交付卡片查询、确认后冻结/解冻、持久化任务、服务端确认、审计和前端操作闭环。新增场景必须复用：

- 单 Agent Runtime 和有界循环；
- Tool Registry 与 Pydantic Schema；
- Task / TaskStep / ToolExecution / ConfirmationChallenge / AuditEvent；
- Application 用例和 Domain 规则；
- OpenAPI → TypeScript 类型生成；
- 合成数据 seed/reset；
- 现有前端任务和确认组件。

不要再造一套 Agent Runtime、确认表、审计表或前端状态机。

## 后端分层

```text
API Router
  -> Application use case
  -> Domain rule / state transition
  -> Infrastructure repository / unit of work
  -> Audit event

Agent tool proposal
  -> Tool Registry validation
  -> Application use case or confirmation challenge
  -> Server-side authorization / policy
  -> Real tool result
```

Agent 不直接访问 ORM Session 或数据库。API Router 不复制业务规则。每个写操作必须有服务端权限、状态校验、幂等和审计。

## 共用实现规则

### 金额

- 金额使用整数最小货币单位；
- 必须带货币代码；
- 不使用浮点数；
- 所有汇总由后端确定性计算；
- 前端只展示后端结果。

### 工具

每个工具至少声明：

- 稳定工具名和版本；
- 输入/输出 Pydantic Schema；
- 资源归属校验；
- 风险等级；
- `confirmation_requirement`；
- 幂等键；
- 结构化错误码；
- 审计元数据。

### 确认

- 写操作先生成确认挑战，不直接改变业务状态；
- 确认绑定操作、参数摘要、资源版本和有效期；
- 确认只能消费一次；
- 参数改变、资源版本改变或挑战过期时拒绝；
- 高风险动作使用复述、二次认证、冷静期或人工接管中的适当组合；
- 读操作通常不需要确认，但必须审计和脱敏。

### 任务状态

沿用现有顶层状态：

`pending`、`planning`、`awaiting_input`、`awaiting_confirmation`、`running`、`completed`、`failed`、`cancelled`。

状态转换由服务端控制；前端只展示，不自行推动。

### 数据与审计

- 只使用合成数据；
- seed/reset 可重复；
- 审计记录 actor、task/tool execution、策略版本、确认、结果和时间；
- 不记录完整卡号、账户号、身份证号、认证凭证或原始敏感载荷；
- 失败和部分成功也要留下真实状态。

## 推荐实施顺序

1. **账单分析**：只读、数据聚合、异常解释。
2. **订阅/代扣**：低风险写操作，确认后暂停/取消/限额。
3. **卡片扩展**：复用已实现的冻结/解冻，增加额度、挂失、补卡等。
4. **智能转账**：先完成账本 ADR，再做转账、幂等、反诈和确认。
5. **理财操作**：固定虚构产品、适当性、风险揭示、模拟申赎。
6. **跨场景联动**：在前五类工具稳定后，做事件驱动和部分成功恢复。

如果团队因比赛范围调整顺序，先更新 `docs/requirements.md`、相关 ADR 和契约，不要直接写代码。

## 场景一：账单分析

### 用户目标

- “这个月钱花哪了？”
- “有没有异常扣款？”
- “帮我做一份本月账单报告。”

### 最小能力

- 查询合成交易；
- 按时间、商户、分类聚合；
- 识别重复/异常交易；
- 生成月度/年度摘要；
- 给出可解释的现金流预测；
- 只读，不改变业务状态。

### 建议工具

- `bills.list_transactions`
- `bills.summarize`
- `bills.detect_anomalies`
- `bills.forecast_cashflow`

### API

建议在 `/api/v1` 下提供查询接口，返回结构化聚合；不要把汇总逻辑放在前端。

### 安全

- 只允许当前 Demo actor 的账户；
- 对商户名、账户尾号等做脱敏；
- 异常结论必须展示依据；
- 不把外部商户描述当指令；
- 不允许 Agent 通过账单工具写数据。

### 测试

- 空账单；
- 跨月/跨年；
- 同商户多笔；
- 退款/冲正；
- 金额精度；
- 他人账户越权；
- 异常解释一致性。

### 完成定义

用户能拿到可重算的分类、趋势、异常和现金流结果；所有数字来自后端；前端能展示解释和来源。

## 场景二：订阅与代扣管理

### 用户目标

- “帮我找出没用的订阅。”
- “这个商户为什么每月扣钱？”
- “把重复订阅停掉。”

### 最小能力

- 订阅/代扣列表；
- 续费提醒；
- 重复/未使用识别；
- 暂停或取消；
- 限额；
- 节省金额报告。

### 建议工具

- `subscriptions.list`
- `subscriptions.detect`
- `subscriptions.pause`
- `subscriptions.cancel`
- `subscriptions.set_limit`

### 风险与确认

- 暂停通常可逆，但仍需说明影响；
- 取消可能不可逆，必须二次确认；
- 不得一次性取消全部订阅；
- 必须区分必要/非必要订阅；
- 必须说明“暂停”和“取消”的差别；
- 商户核验失败时转人工。

### 测试

- 重复订阅；
- 即将到期；
- 取消失败；
- 误取消保护；
- 暂停后恢复；
- 限额修改；
- 跨用户订阅越权；
- 商户名注入。

### 完成定义

用户能看见订阅清单、影响、节省金额和操作结果；取消/暂停不绕过确认；审计可回放。

## 场景三：卡片管理

### 已有能力

卡片查询、冻结/解冻、服务端确认、任务进度、审计和前端操作已实现。不要重写。

### 后续扩展

- 额度调整；
- 交易限制；
- 挂失；
- 补卡；
- 虚拟卡（如团队确认范围）。

### 风险与确认

- 冻结/解冻沿用现有实现；
- 额度调整需身份核验和影响说明；
- 挂失/补卡属于高风险，需强确认或人工；
- 卡号始终脱敏；
- 不允许 Agent 直接调用 ORM。

### 测试

- 非本人卡片；
- 已冻结/已挂失状态；
- 并发确认；
- 重复确认；
- 额度边界；
- 卡片版本冲突；
- 审计一致性。

### 完成定义

新扩展复用现有卡片工具和确认/审计边界；状态变更可验证；前端展示真实服务端状态。

## 场景四：智能转账

### 前置条件

必须先完成账本/余额/币种/交易语义 ADR。没有账本前，不要做“看起来像转账”的假写操作。

### 最小能力

- 按姓名/手机号/备注查找收款人；
- 普通转账；
- 定时转账；
- AA 拆分/收款；
- 余额和限额校验；
- 反诈提示。

### 建议工具

- `transfers.resolve_beneficiary`
- `transfers.validate`
- `transfers.create`
- `transfers.schedule`
- `transfers.split`

### 风险与确认

- 首次收款人、大额、异常设备必须强确认；
- 确认要展示收款人、金额、币种、到账时间、手续费和不可逆性；
- 新收款人/大额可加冷静期；
- 反诈命中时拒绝或转人工；
- 外部网页/客服话术不能绕过确认。

### 测试

- 余额不足；
- 收款人不存在；
- 收款人变更；
- 重复幂等键；
- 相同幂等键不同参数冲突；
- 并发转账；
- 大额/首次收款人；
- 诱导转账；
- 工具超时和未知结果。

### 完成定义

账本状态真实变化；幂等和确认可靠；失败不产生假成功；高风险路径有拒绝/人工接管。

## 场景五：理财操作

### 最小能力

- 固定虚构产品列表；
- 产品对比；
- 风险评估/适当性；
- 模拟申购/赎回；
- 风险揭示和冷静期；
- 不提供真实投资建议。

### 建议工具

- `wealth.list_products`
- `wealth.compare`
- `wealth.assess_suitability`
- `wealth.subscribe`
- `wealth.redeem`

### 风险与确认

- 适当性不匹配时拒绝或降级；
- 必须展示风险、费用、流动性、赎回限制；
- 申购/赎回二次确认；
- 不得承诺收益；
- 不得把全部资金默认投入高风险产品；
- 需要反悔期/冷静期时由服务端执行。

### 测试

- 风险等级不匹配；
- 金额边界；
- 产品下架；
- 重复申购；
- 赎回限制；
- 风险揭示缺失；
- 误导性收益话术。

### 完成定义

模拟订单可追踪；适当性和风险揭示可验证；不存在真实投资建议或真实交易。

## 场景六：跨场景联动

### 目标

在前五类工具稳定后，编排有授权的多步流程：

- 发薪日：账单分析 → 预留 → 还款 → 闲置资金；
- 可疑扣款：账单 → 卡片 → 订阅 → 申诉 → 人工；
- 订阅清理：识别 → 影响说明 → 取消/暂停 → 节省报告。

### 实现原则

- 使用现有 Agent Task 和 TaskStep，不新增第二套工作流；
- 事件触发必须有用户授权和范围；
- 每一步有独立状态、确认和审计；
- 部分成功要明确展示；
- 失败可恢复，不重复已生效步骤；
- 跨场景工具仍调用各场景 Application 用例；
- 不以“自动化”为由跳过确认。

### 事件

建议的领域事件：

- salary_credited
- suspicious_charge_detected
- subscription_due
- card_frozen
- transfer_completed
- dispute_created

事件只触发计划生成，不直接执行资金操作。

### 测试

- 部分成功；
- 中途取消；
- 某一步失败后恢复；
- 事件重复投递；
- 用户未授权；
- 跨场景越权；
- 人工接管；
- 审计链完整。

### 完成定义

一条多步主线能完整演示，且每个高风险节点可解释、可确认、可审计；失败不会伪装成成功。

## 每个场景的 PR 拆分

一个场景至少拆成：

1. 契约/ADR/数据模型；
2. Domain + Application 用例；
3. API + OpenAPI + 生成类型；
4. Agent Tool + 确认/审计；
5. 前端任务/确认展示；
6. 测试与文档。

不要把六个场景塞进一个 PR，也不要在同一迁移里混入多个未评审场景。

## 后端完成清单

- 用户请求进入哪个 API/Task？
- 实际调用了哪个注册工具？
- 谁校验资源归属和权限？
- 确认绑定什么参数和版本？
- 数据库发生了什么状态变化？
- 重复、超时、取消、部分成功会怎样？
- 前端依赖哪个服务端状态？
- seed/reset 能否复现？
- 测试是否断言最终业务状态和审计？
- OpenAPI 和 TypeScript 类型是否同步？

## 当前待确认

- 官方是否仍要求 FATE；
- 正式提交材料和文件格式；
- 官方评分权重；
- 私有仓库如何给评委访问；
- 账本/转账的模拟语义；
- 理财产品范围和合规边界。

这些未确认项不得写死为代码假设；先记录 ADR/待办并取得用户或组委会确认。
