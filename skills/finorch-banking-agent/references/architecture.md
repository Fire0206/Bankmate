# FinOrch 架构与实现指南

## 原则

先读仓库的 `docs/architecture.md`、`docs/agent-contract.md`、`docs/data-contract.md`、`docs/api-contract.md` 和 `docs/security.md`。本文件只补充决策方法，不复制契约。

目标不是“让模型拥有所有权限”，而是让 Agent 在受控工具和策略边界内完成多步骤任务。

## 逻辑分层

- **Web UI**：目标输入、确认卡、风险解释、任务图、审计回放。
- **API**：认证、输入校验、幂等、错误响应、事件流。
- **Application**：编排用例、任务状态、确认流程、人工接管。
- **Domain**：金额、账户、卡片、订阅、转账、理财等业务规则。
- **Infrastructure**：模拟银行核心、数据库、外部适配、日志。
- **Agent**：意图理解、任务图、工具选择、追问、恢复、解释。
- **Security**：授权、风险分级、确认、策略、审计、脱敏。

不要把安全逻辑塞进 UI 或模型提示词。服务端是最终授权和状态变更的边界。

## Workflow 还是 Agent

优先用确定性 workflow：

- 固定字段校验；
- 固定业务规则；
- 金额、限额、权限；
- 幂等和状态迁移；
- 可枚举的确认步骤。

只有以下情况让模型动态规划：

- 用户意图不完整，需要追问；
- 需要在多个工具之间选择；
- 需要组合多个场景；
- 需要解释和恢复。

判断标准：如果缺少最新信息或动态选择会导致答案明显变差，才增加自治；否则用 workflow。

## 工具契约

每个银行工具至少定义：

- 稳定的工具名和版本；
- 类型化输入/输出；
- 调用者身份和授权上下文；
- 幂等键；
- 风险等级；
- 是否需要确认、二次认证或冷静期；
- 可撤销/补偿策略；
- 结构化错误码；
- 审计事件。

工具执行结果必须来自真实工具返回。模型不能自行生成“已转账”“已冻结”“已取消”的结果。

## 风险分级

| 等级 | 示例                               | 默认处理                 |
| ---- | ---------------------------------- | ------------------------ |
| 低   | 查询账单、生成报告、查看订阅       | 可自动执行；记录审计     |
| 中   | 锁卡、暂停代扣、修改限额、取消订阅 | 明确影响 + 二次确认      |
| 高   | 转账、赎回、修改收款人、提升额度   | 二次认证/冷静期/人工复核 |
| 极高 | 大额转账、首次收款人、异常设备     | 强制人工接管或拒绝       |

具体阈值由产品、风控和监管要求确定，不能由模型自由决定。

## 确认设计

确认卡至少包含：

- 操作对象；
- 金额/范围；
- 影响；
- 可逆性；
- 不操作会发生什么；
- 需要的认证方式；
- 用户确认的原文。

高风险操作不能只弹一个“确定吗”。需要根据风险使用复述、二次认证、延迟执行或人工接管。

## 审计事件

建议的审计字段：

- `event_id`
- `case_id`
- `user_id`（脱敏）
- `intent`
- `plan_version`
- `tool_name`
- `tool_input_summary`
- `policy_decision`
- `confirmation`
- `result`
- `timestamp`
- `actor`
- `error_code`

审计日志要支持回放，不记录完整卡号、账户号、身份证号、认证凭证或敏感原始载荷。

## 垂直切片

一次只打通一个场景：

```text
UI 目标输入
  → API 校验
  → Agent 意图/任务图
  → 工具调用
  → 策略与确认
  → 模拟核心状态变更
  → 审计事件
  → UI 结果/回放
```

先做只读账单分析，再做低风险订阅/代扣，再做卡片，再做转账和理财，最后做跨场景编排。

当前仓库已有 Phase 1B 卡片冻结/解冻切片，可作为垂直切片的参考实现：受控工具、服务端确认、持久化任务、状态变更、审计和前端确认组件都已存在。新增场景应复用这些边界，不要复制一套并行的 Agent Runtime 或审计格式。

六场景的具体工具、API、状态和测试拆分见 `references/six-scenario-backend.md`。

## 实现检查

- 金额使用整数最小货币单位，不用浮点数。
- API 路径、字段和错误码遵循仓库契约。
- OpenAPI/Pydantic 是单一事实来源；变更后重新生成前端类型。
- 工具调用有幂等键和超时/重试策略。
- 失败时返回恢复路径，不重复乱调工具。
- 新增行为有正常、边缘和攻击测试。
- 功能状态和文档同步。

## 反模式

- 让模型直接改数据库或调用真实银行接口。
- 只在前端做权限判断。
- 把确认做成一句提示词。
- 工具失败后编造成功。
- 六个场景各写一套工具和审计格式。
- 先做六个页面，最后才接工具和策略。
