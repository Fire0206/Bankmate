# FinOrch 产品与 PRD 指南

## 目标

把“银行 AI 智能体”从功能清单变成可验收的用户任务闭环。PRD 的重点不是描述六个页面，而是定义：

- 用户想完成什么目标；
- Agent 需要哪些工具和多步骤计划；
- 哪些动作需要确认、冷静期或人工接管；
- 什么算完成，什么算失败；
- 哪些能力是 Planned，哪些已经 Implemented。

## PRD 模板

每次新增或修改场景，至少写清楚：

1. **问题**：用户现在为什么做不成？是找不到入口、跨系统来回跳，还是不敢授权？
2. **用户与触发**：谁在什么事件下发起？工资到账、发现陌生扣款、订阅到期、主动查询？
3. **目标与成功标准**：用户要看到什么状态变化或证据？
4. **范围**：本切片包含什么，不包含什么。
5. **工具与数据**：需要哪些受控银行工具、输入输出和合成数据。
6. **确认与风险**：低/中/高风险动作分别怎么处理。
7. **失败路径**：工具失败、意图模糊、权限不足、外部注入、用户反悔。
8. **验收用例**：正常、边缘、攻击各至少几条。
9. **指标**：任务完成率、平均轮次、确认合规率、恢复率等。
10. **状态**：Planned / In progress / Implemented，以及证据。

六个场景都是一级模块。三条演示主线只是把它们串起来，不是只做三个场景。

## 三条主线

### 发薪日资金调度

- 目标：工资到账后分析账单、预留固定支出、处理还款、安排闲置资金。
- 串起：账单分析、智能转账、理财操作、跨场景联动。
- 关键安全：大额确认、适当性、风险揭示、冷静期。

### 可疑扣款处置（当前主 Demo）

- 目标：识别陌生/重复扣款，隔离外部注入，冻结卡片、暂停代扣、生成申诉、转人工。
- 串起：账单分析、卡片管理、订阅/代扣、跨场景联动。
- 关键安全：身份核验、信息脱敏、外部内容隔离、二次确认、人工复核。

### 订阅清理

- 目标：发现未使用/重复/即将到期订阅，解释影响，取消或暂停，生成节省报告。
- 串起：订阅/代扣、卡片管理、账单分析、跨场景联动。
- 关键安全：防误取消、影响说明、商户核验、二次确认。

## 切片顺序

当前已完成 Phase 1A 共享银行底座和 Phase 1B 卡片冻结/解冻垂直切片。不要重复实现已有卡片能力，优先复用其 Agent Runtime、确认、任务、审计和前端组件。

建议的下一步切片：

1. 账单分析（只读、数据基础）
2. 订阅/代扣（低风险写操作）
3. 智能转账（资金操作 + 反诈）
4. 理财操作（适当性 + 风险揭示）
5. 跨场景联动（事件驱动 + 编排）

卡片管理已有冻结/解冻切片，后续扩展额度、挂失、补卡时再单独设计。平台能力并行开发，但每次只打通一个垂直切片。

## 场景完成定义

- 用户目标能通过真实工具闭环完成。
- 至少两条失败路径有恢复方案。
- 至少一个安全卡点可见、可测试。
- 至少一个交互创新点可演示。
- 有 8—10 条评测任务和对应结果。
- 契约、文档和实现状态同步。

## 非目标

- 不在比赛阶段接真实银行、支付或征信系统。
- 不用真实用户数据做演示。
- 不把“模型能回答”当作“任务已完成”。
- 不为六个场景各造一套独立 Agent。
- 不把线框图、PPT 或 Demo 脚本当成已实现能力。

## 当前仓库资料

在 FinOrch 仓库中，设计探针位于 `docs/competition/demo-template/`。这些材料可以改，不应反向限制 PRD；如果设计方向改变，先更新 PRD 和决策记录，再更新演示材料。当前卡片切片已经实现，但整个“可疑扣款处置”主线仍需要补账单、订阅和跨场景能力；不要把设计探针当成已完成产品。

后端实现拆分、工具/API/确认/审计和六场景验收清单见 `references/six-scenario-backend.md`。
