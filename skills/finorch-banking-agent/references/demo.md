# FinOrch 比赛演示指南

## 叙事

对外：一个懂用户的个人财务管家，一句话把事办完。

对评委：一个让银行 Agent 办得成、拦得住、查得清的可信执行平台。

封面和开场用“管家”，架构和安全页用“平台”。

## 三分钟主 Demo

当前默认主线：可疑扣款处置。

当前仓库已实现模拟卡片冻结/解冻和确认流程，但“可疑扣款处置”还需要账单分析、订阅/代扣、可疑交易识别、申诉和人工接管等能力。Demo 中必须把已实现部分和 Planned 部分分开说。

| 时间      | 内容                                                                    |
| --------- | ----------------------------------------------------------------------- |
| 0:00—0:20 | 陌生扣款后，用户在账单、客服、卡片之间来回跳                            |
| 0:20—2:20 | 调查、发现重复扣费、隔离注入、确认冻结/暂停、生成申诉、转人工、审计回放 |
| 2:20—2:50 | 架构、评测指标、商业价值                                                |
| 2:50—3:00 | 前台是管家，后台是平台                                                  |

详细台词见仓库 `docs/competition/demo-template/DEMO_SCRIPT.md`。如果产品方向改变，先改脚本，不要硬套旧台词。

## 10 页答辩

1. 封面 + 一句话定位
2. 问题：功能碎片化 + 不信任自动操作
3. 六场景矩阵 + 三条主线
4. 主 Demo before/after
5. 产品体验：对话 + 确认卡 + 财务总览 + 审计
6. 架构：交互、Agent、工具、可信执行、评测
7. 安全：权限、风险分级、注入隔离、人工接管、审计
8. 评测：任务成功率、拦截率、轮次、恢复率
9. 商业价值：客服成本、损失阻断、卡片活跃、留存
10. 团队与路线图

## 线框图原则

- 对话负责目标和追问，结构化面板负责复杂信息。
- 高风险动作必须全屏/强提示确认，不能压缩成一行。
- 每个建议都能展开“为什么这么做”。
- 审计回放是产品的一部分，不是后台日志。
- 手机端对话优先，任务图和审计放“案件详情”。

## 评委问答

### 和普通客服机器人的区别？

它会调用受控工具改变业务状态，并在资金/状态变更前做权限、风险解释、确认和审计。

### 怎么防止乱转账？

服务端权限 + 工具限额 + 风险分级 + 二次确认/冷静期 + 人工接管 + 审计，不靠一句提示词。

### 六个场景是不是六个 Demo？

六个是一级模块，共享 Agent、工具、策略和审计；三条主线只是演示顺序。

### 怎么证明不是套壳？

展示真实工具调用、状态变化、失败恢复、攻击用例和评测记录。

### 商业价值怎么量化？

账单争议成本、欺诈/重复扣费损失、客服转人工率、卡片活跃、客户留存。不要编造精确财务数字。

## 演示失败模式

- 只演示成功路径。
- 只讲技术栈，不讲用户目标。
- 安全变成口头承诺。
- 指标是占位符却当成实测。
- 把 Planned 功能说成已实现。
- 现场网络/模型失败没有录屏或 mock 兜底。

## 演示纪律

- 所有业务指标由团队实测或明确标为示例。
- 只使用模拟核心和合成数据。
- 至少彩排三次，控制在三分钟。
- 准备离线录屏和固定种子数据。
