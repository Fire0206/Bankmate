# 架构建议（Phase 0.5）

**核对日期：2026-10-18**

**状态：建议，待 Phase 1 采用；不是已实现架构或新 ADR。**

本文件依据 [Phase 0 架构](../architecture.md)、[Agent/Tool/Workflow 契约](../agent-contract.md)、[数据契约](../data-contract.md)、[安全设计](../security.md)和本轮[源码审查](open-source-review.md)给出实施建议。Phase 0.5 不修改这些既有契约，也不增加运行时代码或依赖。发生架构冲突时，现有仓库文档仍是当前约定；采纳本建议时应通过对应 ADR 更新。

## 建议摘要

| 领域           | 建议                                                                                                             | 理由与边界                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 总体架构       | **Adopt：** 继续模块化单体；按 API、Application、Domain、Infrastructure、Agent、Security 的职责边界组织实际代码  | 当前规模和团队可以共用一个 FastAPI 服务、一个 React 应用和一个 SQLite 数据库；避免提前维护微服务及分布式事务 |
| API 与类型     | **Adopt：** FastAPI/Pydantic 生成 OpenAPI，作为 API Schema 单一事实来源；前端类型自动生成                        | 避免前后端手工类型漂移；接口变化需在一个 PR 内更新契约、生成类型和消费者                                     |
| 业务存储       | **Adapt：** SQLite + SQLAlchemy + Alembic，所有业务数据使用固定合成数据和可重复 seed                             | 足以支持本地演示和小规模并发测试；只在验证出锁竞争/多进程需求后再评估其他数据库                              |
| 金额与账务     | **Adopt：** API/工具使用整数最小货币单位；确定性规则在后端；如实现转账，使用小型双分录账本和单事务写入           | 避免二进制浮点误差；余额、流水、幂等记录和审计可一起验证                                                     |
| Agent          | **Adapt：** 模型无关 Provider + 一个有步骤上限的 Agent 调用循环 + 注册表中的受控工具                             | 先满足单一任务的规划、澄清、确认和执行；模型输出仅为不可信提议，不可访问数据库                               |
| Workflow       | **Adopt：** 将任务、步骤、工具执行和确认存入应用数据库；服务端负责状态迁移                                       | 可中断、恢复、查询真实执行结果；前端不伪造状态                                                               |
| 前端           | **Adopt：** React/TypeScript/Vite/Tailwind；需要服务端缓存时再按需加入 TanStack Query，需要图表时再评估 Recharts | 延续现有基础设施；不先搭复杂 Dashboard 或组件体系                                                            |
| 框架和外部系统 | **Defer：** LangGraph、Google ADK、MCP、多 Agent、Redis、Kafka、Kubernetes、真实银行/支付 API                    | 当前没有足以支持这些依赖的产品或运维需求；若出现持久化图恢复、外部工具互操作等具体需求，先做 ADR             |

“Adopt/Adapt/Defer”表示建议的决策状态，不表示已开发或已引入。源码项目的具体证据及许可证风险见[开源项目审查](open-source-review.md)。

## Banking Core 与数据边界

### 金额、余额和账本

- 金额以整数最小单位传输和持久化，例如 USD 12.34 表示为 `amount_minor: 1234`；货币代码使用 ISO 4217 大写代码，并依据货币的小数位解释最小单位。币种精度应由服务端受控表决定，不能由模型或浏览器临时推断。
- 禁止使用 `float`/JavaScript `number` 对金融金额做精确运算。显示层可格式化为十进制字符串；输入必须先按币种精度解析，再由后端验证范围。
- 余额的唯一事实来源要在 Banking Core ADR 中定清。建议以不可变的模拟账本分录为事实来源；余额由分录聚合。若之后为了查询加入缓存余额，必须与账本在同一事务更新，并有重算校验。
- 转账执行应在同一数据库事务中验证账户状态、归属、币种、正金额和可用余额，并写入转账、借贷分录、幂等记录与审计事件。任一约束失败则整体回滚。账户初始余额应由可重放 seed 写为明确的期初分录。
- 不支持真实银行接口、真实资金移动或真实账户数据。Phase 1 用固定虚构主体、账户、卡片、交易、账单和产品。

### SQLite 与迁移

- 初期选 SQLite 的理由是本地无需独立服务、容易重置演示数据、可在 CI 运行；SQLite 只有单写者，不能据此承诺高并发生产语义。官方文档说明其隔离与写事务行为：[Isolation In SQLite](https://www.sqlite.org/isolation.html)、[Transactions](https://www.sqlite.org/lang_transaction.html)。
- 使用 SQLAlchemy 管理会话/事务，以 Alembic 管理已提交迁移。迁移由 Banking Core/数据负责人集中维护；业务模块通过 Application 用例和仓储边界读写，不各自创建连接或重复业务规则。
- 需在集成测试中覆盖并发写、锁等待、超时和重试结果。SQLite 的 busy timeout 只能改善短时锁等待，不等于多写者扩展能力。若之后真实需求超出 SQLite，另立 ADR 并规划迁移。
- 为演示数据提供明确的 `seed` 与 `reset` 命令，要求重复执行后得到同一状态；重置只能作用于指定的本地/测试数据库，不可默认删除任意路径的数据。
- 持久化实体建议使用稳定主键、UTC 时间、明确状态、创建/更新时间和必要的版本字段。表/模型用单数 `snake_case`，主键 `id`，外键 `<entity>_id`；金额用 `<name>_minor` 与 `currency`，状态用受限枚举。

### 区分数据类别

| 数据类别   | 例子                                                             | 生命周期与限制                                                                   |
| ---------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 业务数据   | Account、Card、Transaction、Subscription、InvestmentOrder        | 仅虚构数据；由 Banking Core 用例变更；需要 migration/seed                        |
| Agent 状态 | WorkflowTask、WorkflowStep、ToolExecution、ConfirmationChallenge | 记录真实服务端状态和重试边界；对输入/输出保存最少必要摘要，避免存储整段敏感提示  |
| 审计记录   | actor、策略版本、工具/任务 ID、结果状态、时间、幂等摘要          | 追加式；与业务变更同事务记录；字段脱敏，不写密钥、认证头、PIN 或不必要的原始输入 |

具体实体和字段最终以现有[数据契约](../data-contract.md)及 Phase 1 的 schema PR 为准；此处不要求一次性创建六场景所有表。

## Agent、工具与安全建议

### 最小 Agent 运行形态

1. 定义可替换的 Provider 端口：输入有版本、超时和 token/步骤预算；默认测试使用 Fake Provider。若未来配置 OpenAI-compatible API，密钥仅从本地环境/私有密钥配置读取，绝不写入日志或前端。
2. Agent 仅可选择已注册工具；每个工具由服务端维护名称、描述、版本、Pydantic 输入/输出 schema、权限级别、风险级别、确认要求和幂等策略。
3. 用有最大步骤数/超时的单 Agent 循环完成一次请求。解析失败、未知工具、工具超时或模型调用失败均转成明确的错误/等待状态，不编造执行结果。
4. 所有工具调用走既有生命周期 `Validation → Authorization → Confirmation → Execution → Audit`。Agent 不直接访问 SQLAlchemy Session、数据库文件、环境密钥或任意网络地址。
5. 账户余额、金额校验、资源所有权、卡片权限、风险级别和确认是否有效全部是服务端确定性规则。提示词里的“已批准”或模型 JSON 的角色字段不能授权操作。

检索内容、用户文本、附件、工具返回及网页文本一律视作不可信数据。Prompt Injection 防护以权限最小化、输入边界、输出 schema 校验、工具 allowlist、确认挑战和审计为主；系统提示词不是授权机制。日志采用 allowlist 字段，使用当前[安全设计](../security.md)的脱敏约定。

### 高风险确认挑战

对资金移动、不可逆操作、权限提升及高风险敏感变更，服务端创建一次性确认挑战，最少绑定：`challenge_id`、actor、工具及版本、规范化参数摘要、目标资源 ID 与版本、风险/策略版本、幂等键、过期时间和消费状态。前端显示来自服务端的实际影响。确认请求到达时重新检查授权、资源版本、策略和幂等状态；任何影响参数变化都使旧挑战失效并要求重新确认。挑战的消费和副作用应处于同一事务边界，或有可审计的等效防重机制。

即便是可逆的模拟卡片冻结，也应在服务端鉴别资源归属、状态和调用者；是否要求人工确认按安全策略确定。试点切片建议确认冻结/解冻，以完整验证服务端路径，但不把该选择描述为赛事要求。

### 幂等、失败和结果未知

- 幂等键按 actor、操作/工具版本和作用域唯一；保留规范化输入哈希与结果引用。相同键、相同输入返回已保存结果；同键不同输入返回稳定冲突错误。
- 数据库唯一约束是最终防线；“先查询再写”的应用级检查本身不能解决并发竞争。并发测试应断言只有一次状态变更、一次关键审计结果，并收到一致响应。
- 对已发生但响应丢失的操作，先按幂等键查询结果再决定状态；不得盲目再次执行。无法判定时返回 `unknown`/人工介入状态，而不是伪报成功或失败。
- Workflow 部分完成时保留已完成步骤，标明后续步骤失败/取消；不要宣称整个多步任务原子回滚。补偿动作必须是显式业务用例并独立审计。

## Workflow 与前端进度

保持现有状态协议：`pending`、`planning`、`awaiting_input`、`awaiting_confirmation`、`running`、`completed`、`failed`、`cancelled`。Task 描述用户目标；Step 表示有序业务步骤；ToolExecution 记录一次实际服务端工具尝试；ConfirmationChallenge 关联待确认的确定参数。终态不可原地重启；新尝试需新增 attempt 或 task 记录。

Phase 1 首选 REST 读取任务和进度的轮询方式，降低实时推送与断线恢复复杂度；轮询间隔和退避由前端控制，服务器返回单调递增版本/更新时间。当前 Agent 契约中 SSE 是计划选项；若有低延迟或长任务展示的可验证需要，再经 ADR 比较 SSE、轮询和 WebSocket，而非同时实现多种通道。

前端以 API 返回的任务状态作为真相：状态卡展示任务、步骤、确认等待、失败原因和最后更新时间；加载、空数据、过期/重试、网络中断均有明确界面。不能仅播放本地动画来表示实际执行。OpenAPI 生成类型是 API 类型来源；MSW 可根据契约为前端并行开发提供本地模拟响应，但生产 UI 仍应依据 API 的真实状态。

## 框架与依赖决策

| 技术                          | 建议                                        | 触发重新评估的证据                                                                                                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQLAlchemy + Alembic          | Phase 1 需要实际持久化时引入                | 当前已规划为后续数据层；由 ADR 确认同步/异步接口、迁移流程和 SQLite 约束                                                                                                                                                                                                      |
| React Router / TanStack Query | 需要多页面路由/复杂服务端缓存时再引入       | 先看任务进度、失效和错误状态是否已超出当前轻量状态管理                                                                                                                                                                                                                        |
| shadcn/ui                     | 有稳定设计 token 和重复组件需求后再按需加入 | 保持组件源码归属、可访问性与许可检查；不提前批量生成组件                                                                                                                                                                                                                      |
| LangGraph                     | 暂缓                                        | 需要跨进程持久化图执行、长时 interrupt/resume、复杂分支后，证明自有 Workflow 表不足；再比较依赖和运维成本。官方能力参考：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) |
| Google ADK                    | 暂缓                                        | 仅在确实决定使用 Google 模型/Vertex 生态且接受平台耦合时比较；当前抽象要求模型供应商可换。官方说明见[ADK 文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/adk)                                                                                      |
| MCP                           | 暂缓                                        | 至少两个独立进程/团队需要标准化工具互操作，且身份、权限、审计和传输策略已定义后，再评估。内部 Python 工具先走 typed registry                                                                                                                                                  |
| Multi-Agent                   | 暂缓                                        | 单 Agent 有明确可测的上下文/职责瓶颈，且拆分可以改善指标并保留一个权限边界时，才提出 ADR                                                                                                                                                                                      |
| Redis、Kafka、Kubernetes      | Phase 1 不引入                              | 有真实跨进程锁、异步吞吐、部署拓扑或可用性指标证明必要性后分别评审                                                                                                                                                                                                            |

## 应形成 ADR 的事项

本轮不创建或更改 ADR。Phase 1 进入实现前建议优先由团队决定并记录：

1. 模拟账本事实来源、货币精度元数据与余额读取方案。
2. SQLAlchemy 同步/异步使用方式、SQLite 文件位置、migration、seed/reset 的危险路径保护。
3. 确认挑战的数据模型、有效期和单次消费事务边界。
4. Agent 最大步数/超时、Fake Provider 端口和可选兼容模型配置。
5. 任务进度接口是轮询还是事件推送（仅当轮询不满足需求时）。
6. Phase 1 场景次序和每个场景的安全级别、确认要求。

比赛强制要求、版权/授权和公开时间目前未核实；不得用技术建议替代赛事规则。官方检查记录位于[研究索引](README.md#赛事来源及待核实事项)。
