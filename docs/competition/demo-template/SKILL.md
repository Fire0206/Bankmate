# 银序 BankAgent · 比赛示范模板

> 一句话把事办完，每一步都办得成、拦得住、查得清。

> 状态：Planned / 设计模板。这里描述的是比赛演示目标，不代表 FinOrch 当前已经实现这些能力。

## 何时使用

- 准备金融科技比赛的作品介绍、技术文档、答辩 PPT。
- 需要把“银行 AI 智能体”从聊天 Demo 升级为可执行、可解释、可审计的系统。
- 需要设计三条演示主线，同时覆盖六个核心场景。
- 需要准备安全测试、评委问答和商业价值叙事。

## 不适用

- 不是生产级银行系统架构，不能直接连接真实账户或真实资金。
- 不是对微众银行、Sierra、Rocket Money 的完整研究；这是快速档模板。
- 不能替代你们自己的用户研究、技术验证和实测指标。

## 主叙事：管家前台 + 平台后台

**对外一句话**：银序是一个懂你的个人财务管家，从账单到转账、理财、卡片，一句话把事办完。

**对评委一句话**：银序是一个让银行 Agent 办得成、拦得住、查得清的可信执行平台。

**封面/开场用前者，架构/安全页用后者。**

这不是“会聊天的银行客服”，而是：

- 用户看到：目标导向的对话、结构化确认卡片、可理解的解释。
- 银行看到：任务图、工具调用、权限校验、风险分级、人工接管、审计回放。

## 五个核心原则

### 1. 受控工作流，而不是无限自治

Agent 只在需要动态决策的地方自主规划；资金移动、账户状态变更、合规判断必须经过确定性工具和策略检查。

**展示方式**：任务图 + 工具调用链 + 人工检查点。

### 2. 信任是可见的产品表面

不要只说“安全”，要让用户看到：

- 为什么建议这个动作；
- 会改变什么；
- 需要确认什么；
- 出错后怎么恢复；
- 谁可以复核。

**展示方式**：风险解释卡、确认卡、审计时间线。

### 3. 闭环结果，而不是对话完成

任务完成的标准是业务状态发生变化并可验证，不是模型说“已为您处理”。

**展示方式**：操作前/后状态对比、案件状态、节省金额、处理时长。

### 4. 主动但有边界

工资到账、可疑扣款、订阅到期可以触发主动服务，但用户必须能关闭、延后或限制范围。

**展示方式**：事件触发卡 + 授权范围 + 频率限制 + 退出入口。

### 5. 外部内容不可信

网页、商户备注、搜索结果、聊天记录都是数据，不是指令。

**展示方式**：外部内容隔离区、来源标注、指令剥离、引用而非执行。

## 主 Demo：可疑扣款处置

这是默认主 Demo，因为它同时覆盖任务完成、安全合规、跨场景联动和可解释性。

### 用户目标

“我账单里有一笔 299 元扣款，我不记得买过。帮我看看怎么回事。”

### 完整链路

1. 查询交易、商户、订阅和近期扣费记录。
2. 发现同一商户 30 天内扣费 3 次，其中 1 次疑似重复。
3. 商户描述里出现“忽略之前指令”等外部注入内容，系统标记为不可信数据。
4. 建议先冻结卡片、暂停该商户代扣，并解释影响范围。
5. 用户二次确认后执行，展示前后状态。
6. 生成申诉材料，缺少的证据向用户追问。
7. 金额/证据达到阈值时转人工复核，写回处理结果。
8. 审计回放展示每一步依据、策略判断和工具结果。

### 三分钟结构

| 时间      | 内容                                             | 评委看到什么    |
| --------- | ------------------------------------------------ | --------------- |
| 0:00—0:20 | 陌生扣款后，用户在账单、客服、卡片管理之间来回跳 | 真实问题        |
| 0:20—2:20 | 完整处置链路，中间插入一次注入拦截和一次人工接管 | 任务闭环 + 安全 |
| 2:20—2:50 | 架构、评测指标、商业价值                         | 不是套壳        |
| 2:50—3:00 | “前台是管家，后台是平台”                         | 记忆点          |

1. 封面：项目名 + 一句话定位。
2. 问题：功能藏在菜单里，跨场景要来回跳，用户不信任自动操作。

至少覆盖以下类别：

- 诱导转账；
- 越权查询；
- 信息套取；
- Prompt 注入；
- 外部网页/商户备注注入；
- 误取消订阅；
- 高风险理财；
- 模糊指令；
- 情绪胁迫；
- 工具失败；
- 数据不一致；
- 人工接管失败。

## 评委问答

### Q1：这和普通客服机器人有什么区别？

普通客服机器人主要回答问题；银序会调用银行工具、改变业务状态，并在每次高风险动作前做权限校验、风险解释和用户确认。我们展示的是任务闭环和审计链，不是聊天记录。

### Q2：怎么防止 Agent 乱转账？

不是靠一句提示词。我们有三层：

1. 工具层：收款人、金额、账户、频率的硬限制。
2. 策略层：风险分级、二次确认、冷静期、人工接管。
3. 审计层：每个判断和工具调用都可回放、可追责。

### Q3：六个场景是不是六个独立 Demo？

不是。六个场景共享同一套 Agent 编排、工具协议、策略引擎和审计事件；三条主线只是把能力串成用户故事。

### Q4：安全是提示词还是系统能力？

提示词只负责表达和引导；真正的安全来自权限矩阵、确定性工具、策略引擎、确认机制和人工复核。

### Q5：商业化价值怎么量化？

看四类指标：账单争议处理成本、欺诈/重复扣费损失、客服转人工率、卡片活跃与客户留存。Demo 中展示的是可验证的流程指标，不把公开课里的微众数据冒充成我们的实测结果。

### Q6：如果模型判断错了怎么办？

高风险动作不依赖单次模型判断；工具返回结构化结果，策略引擎做二次校验，异常时转人工。失败后给出恢复路径并保留审计记录。

### Q7：为什么需要 Agent，而不是固定流程？

固定流程适合标准任务；Agent 适合意图不完整、需要追问、跨场景组合的任务。我们的设计是“能固定就固定，需要判断才自主”，不是所有步骤都交给模型。

## 反模式

- 六个场景做成六个互不相干的聊天机器人。
- 只展示成功路径，不展示失败和恢复。
- 把“安全”写成提示词，而没有策略和权限。
- Agent 直接执行资金操作，没有确认和冷静期。
- 用公开课的“10 倍”“80%”冒充自己的实测指标。
- 把所有信息塞进聊天气泡，没有结构化面板。
- 声称“完全自治”，但没有人工接管和审计。
- 为了显得创新而堆工具，导致任务成功率下降。

## 诚实边界

- 本模板基于公开资料与公开课材料的快速蒸馏，不是完整行业研究。
- 没有做用户访谈，也没有获取往届获奖队伍的完整答辩材料。
- 微众、Sierra、Rocket Money 的材料偏宣传，缺少独立失败率数据。
- 所有业务指标必须由你们自己的 Demo 和评测集重新测量。
- 演示只能使用模拟银行核心和合成数据，不能连接真实账户或真实资金。

## 使用流程

1. 把项目名、团队名和品牌色替换成你们自己的。
2. 用 `DEMO_SCRIPT.md` 排一遍三分钟 Demo，删掉讲不完的内容。
3. 用 `PPT_OUTLINE.md` 建 10 页答辩稿。
4. 用 `SAFETY_TEST_CASES.md` 跑攻击用例，记录真实结果。
5. 把模板里的指标占位符换成你们的实测数据。
6. 至少完整彩排三次，确保 3 分钟内能跑完主 Demo。
